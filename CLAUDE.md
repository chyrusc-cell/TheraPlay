# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

TheraPlay is a therapy-activity web app. It is two projects in one repo: a React 19 + Vite + Tailwind CSS v4 frontend at the repo root (`src/`) and a Laravel + Sanctum JSON API in `backend/` (MySQL in dev). The root `README.md` is the unmodified Vite template and `backend/CLAUDE.md` / `backend/AGENTS.md` are generic Laravel Boost setup guidelines; neither describes this app.

## Commands

Frontend (repo root):
- `npm run dev` — Vite dev server. `npm run build` — production build. `npx eslint src` — lint (run it after edits; `npm run lint` lints the whole repo, including `backend/vendor`, so it reports unrelated errors).
- Frontend tests (Vitest + React Testing Library + jsdom; config in `vitest.config.js`, setup/helpers in `src/test/`, tests are `src/*.test.{js,jsx}`): `npm run test:run` runs them once, `npm run test` watches, `npm run test:coverage` adds a coverage report. They never touch the network: `fetch` is replaced by `mockApi()` (`src/test/helpers.jsx`), any unmocked request throws, and the API address is a fake host (`http://api.test/api`). `AppRoutes` is exported from `TheraPlay.jsx` so tests can render the real route table in a `MemoryRouter`. A test marked `it.fails` records a known app bug (there are none at the moment); when the bug is fixed that test fails, so turn it into a normal `it`.

Backend (`cd backend`):
- `composer run dev` (same as `php artisan dev`) — starts the API server and the root Vite frontend together (`frontend` + `server` processes, registered in `AppServiceProvider`; the default `queue` and the backend's own `vite` are excluded). Needs `npm install` in `backend/` once (for `concurrently`); stop any servers already using ports 8000/5173 first.
- `php artisan serve --host=127.0.0.1 --port=8000` — API only; the frontend hardcodes `http://127.0.0.1:8000/api`.
- `php artisan test` — full suite (sqlite in-memory, config in `phpunit.xml`, which sets a throwaway `APP_KEY`). One file/test: `php artisan test --filter=ProfilePhotoTest` or `--filter=test_name`.
- `php artisan migrate` — apply pending migrations. New features regularly add migrations; the dev DB (`theraplay_db`) is not migrated automatically, and an "Unknown column"/missing-table error usually means one is pending (`php artisan migrate:status`).

Windows notes: PHP comes from Herd and is not on the Git Bash PATH — run `php`/`artisan` from PowerShell. The dev server is `php -S` and reads Herd's `php.ini` (`C:\Users\<user>\.config\herd\bin\php85\php.ini`), so upload limits (`upload_max_filesize`, `post_max_size`, `upload_tmp_dir`) are set there and only apply after the server is restarted. App-level limits: contact photo and profile picture 2 MB, activity picture 5 MB, attached materials 10 MB each.

## Frontend architecture

- **Routing/layout** (`TheraPlay.jsx`, `Layout.jsx`): auth pages (login/register/forgot/reset) have no layout; everything else renders inside `Layout`, which wraps `AuthProvider`, a fixed `Sidebar`, a fixed floating `GlobalSearch` pill, a fixed top-right profile shortcut, and an empty `h-topbar` (56px) spacer row. The sidebar is a floating rounded panel (`--sidebar-gap`, 12px; 8px at ≤560): it is positioned with `top/bottom/left-sidebar-gap`, and the page and the search pill start at `--sidebar-offset` / `--sidebar-offset-collapsed` (width + 2 gaps; `ml-sidebar-offset`), not at the bare `--sidebar-width`. Admin routes sit under `<RequireRole role="admin">`; that is UX only — the backend `role` middleware is the real protection.
- **Session**: "Remember me" is on by default (token in localStorage; unticked = sessionStorage for the tab). `GuestOnly` (login, register, forgot-password only; NOT reset-password or verify-email) checks the token with `GET /api/user` and redirects a logged-in user to `homeFor(user)`; `SessionWatcher` (inside `Layout`) sends a page to login when the token disappears behind it (back/forward-cache `pageshow`, or logout in another tab). `AuthProvider` verifies once per `Layout` mount and pages use its `user` (do not fetch `/user` again). In dev, StrictMode doubles effects, so `/user` shows twice; production makes one request.
- **Auth**: Sanctum personal access token stored as `theraplay_token` in localStorage or sessionStorage. `api.js` has `apiRequest()` (returns `{ok,status,data}`, adds the Bearer token, handles `FormData`), `clearSession`, `mapValidationErrors`. `AuthProvider` verifies the user once via `GET /api/user`; `useAuth()` gives `{status, user, retry, updateUser}`. Role-dependent UI (sidebar, search results) must come from this server-verified user, never from storage. Pages that call `fetch` directly now import `API_URL`/`getToken` from `api.js` (Stage 4 removed the duplicate `getToken` copies).
- **Children**: a parent has several children. `ChildProvider` (in `Layout`, below `AuthProvider`) is the one source of truth for the selected child (`useChildren()`); the top-bar `ChildSelector` changes it, the choice is remembered per account in localStorage as a preference only and is cleared by `clearSession`. Child-dependent pages (Activities, Dashboard, Progress, completing an activity) use `useChildGate()` and send `child_id`; the backend resolves it with `ResolvesChild` among the caller's own children only (another parent's id is a 404). The Activities page lists ALL published activities for every parent (`GET /api/activities` is the plain public list); a child's conditions and the admin activity–condition assignments (`activity_condition` pivot, `is_for_all_conditions`) are kept but do not filter what parents can browse — the selected child only decides the completed marks.
- **Styling**: Tailwind v4 CSS-first (`src/css/tailwind.css`, `@theme`, `@custom-variant`). Preflight is deliberately not imported. Breakpoints are named variants (inclusive max-width): `laptop` ≤1100, `tablet` ≤900 (sidebar collapses to a 72px rail), `tablet-sm` ≤800, `phone-lg` ≤720, `phone` ≤560 — use these, not `max-[…]`. Design tokens live once in `:root` of `src/css/ui.css` (the Warm Neutral palette: `--ui-page`, `--ui-edge`, `--ui-accent`, …) and are exposed as Tailwind colors (`bg-page`, `border-edge`, `text-muted`, `bg-accent`, …) — use those, not hex values, for neutrals; semantic green/red/amber and the brand logos stay hardcoded. `ui.css` also holds keyframes, the global `prefers-reduced-motion` rule, and a few intentionally unlayered rules (unlayered CSS beats Tailwind's layered utilities). Class strings are shared through `uiClasses.js` (page container/heading: `pageMain`, `pageTitle`, …), `adminClasses.js` (admin forms/tables), `authClasses.js`; write class strings out in full so Tailwind can see them.
- **Buttons** (updated in Batch 5; the old `btn-solid`/`btn-tone` text was out of date): one glass 3D look lives in `src/css/tailwind.css` as the `btn-glass` utility (conic edge ring, sheen, inner light, settle-in on hover) applied to the element itself, never a wrapper. Colour is a separate modifier class that only changes the `--btn-*` tokens (`src/css/ui.css`, "Button colors"): `btn-white` (the default look: manage/navigate/cancel/refresh/select/archive/replace/send), `btn-green` (create/save/publish), `btn-yellow` (edit/change), `btn-red` (delete/unpublish/log out). **There are no blue or gray buttons** (`btn-blue`/`btn-gray` were renamed to `btn-white`). Red `224 112 130`, yellow `236 226 128`, green `124 187 138` are muted versions of #FF0055 / #FFFF69 / a true green (not #00FFFF); labels are dark shades of each hue. `src/Button.jsx` (`variant` primary/secondary = white, danger red, success green, ghost). Shared class strings: `adminClasses.js` (`fileReplace` white, `fileRemove` red, `archiveButton` white, `unpublishButton` red, `viewSwitch`/`viewSwitchButton` for the Activities/Archived switch, `filterSelect`), `uiClasses.js` (`smallActionClass`). Icon-only controls, the search pill and star ratings are intentionally not glass buttons.
- **Loading pattern**: data pages load in a `useEffect` with an `AbortController`, show a skeleton from `Skeleton.jsx`, and call `holdSkeleton(startedAt, signal)` (`minLoading.js`) in `finally` so skeletons stay ≥500 ms without delaying the request; check `signal.aborted` before setting state.
- **Private images**: uploaded images live on the private disk, so `<img>` can't fetch them with a token. Public ones use public URLs; the user's own picture (`ProfileAvatar.jsx`) and an admin's view of a draft activity's picture are fetched with the token and shown via blob URLs (revoked on cleanup).
- **Motion**: `Collapsible.jsx` (grid-rows 0fr→1fr) for expand/collapse; entrance animations use the `ui-*` keyframes in `ui.css`.

## Backend architecture

- All routes are in `backend/routes/api.php`. Admin routes are one group: `auth:sanctum` + `role:admin` (alias for `EnsureUserHasRole`) under `/api/admin`. Parent-only routes use `role:parent` (completion, feedback, child creation). Login and register are throttled (see Stage 4 for the separate limiters).
- **Roles**: `parent` and `admin`; `role` is not mass-assignable (set with `forceFill`). Activities CAN be permanently deleted: `DELETE /api/admin/activities/{activity}` (admin only) deletes the activity AND, by design, every child's progress record for it (approved by the owner; this reverses the earlier "no delete, unpublish instead" safeguard). `ActivityManagementController::destroy` removes the progress, resource and `activity_condition` rows plus the activity in one transaction, then deletes the picture and uploaded material files from the private disk only after the commit (a failure rolls everything back and keeps the files). Other activities, children and parents are untouched. Permanent deletion is allowed ONLY for an ARCHIVED activity (Stage 2): `DELETE` on a live activity returns `409 activity_not_archived`, and the Delete button exists only in the Archived Activities view. The Delete permanently button (archived view) opens a `ConfirmDialog` (danger button) naming the activity and warning that its progress history, attachments and picture are removed too. Unpublish still hides an activity without losing anything. `UserManagementController` (Manage Accounts): `POST /admin/users` always creates an ADMIN (any client `role` is ignored; the new address is unverified and gets a verification email), roles change only through `POST /admin/users/{user}/promote|demote` (never through update, which takes name/email only), and the last-admin / self / has-children checks run in a transaction that locks the admin rows. It refuses to delete or demote yourself or the last admin, and to delete accounts with child profiles (same rule as self-service deletion). `php artisan user:promote-admin <email>` remains the setup/recovery path.
- **Uploads/images** (activity materials, `activity-images/`, `contact-photos/`, `profile-photos/`): stored on the private disk named by `config('filesystems.activity_materials.disk')`. Paths are generated server-side only (the `image_path`/`photo_path` columns are never fillable or accepted from requests); API responses expose a `*_url` accessor, never the path. Validation uses the `ValidatesImageUploads` trait (real MIME sniff + `getimagesize`, not the client's type). Replacing/removing/deleting the owner deletes the old file, restricted to the expected folder. Public image routes serve only published activities / listed contacts; a profile picture is readable only by its owner.
- **Email and account safeguards**: `User` implements `MustVerifyEmail`. Verification and email-change links are time-limited, RELATIVE-signed URLs (`VerifyEmailAddress::signedPath`) that point at the React page `/verify-email`, which POSTs them to the public `POST /api/email/verify/{id}/{hash}` (the only place an address becomes verified). A requested new address is a *pending email* kept in the cache (not the users table; needs a persistent `CACHE_STORE`, not `array`) until its link is opened; changing it requires `current_password` (`PUT /api/profile`). Parents created at/after `EMAIL_VERIFICATION_ENFORCED_FROM` (empty = off; older accounts and admins are never held) are refused with `403 email_not_verified` by `RequireVerifiedEmailWhenEnforced` on every API route except `user`, `logout`, `email/*`, `profile*`; the app shows `GatedOutlet` for them. `DELETE /api/profile` (password required) deletes only the token's own account and refuses admins and accounts with child profiles (children.user_id cascades to progress). Mail uses `MAIL_MAILER` (`log` locally; see `.env.example` for SMTP/Gmail); responses say `delivered: false` rather than "sent" for the `log`/`array` drivers (`App\\Support\\MailDelivery`). Every throttled route uses its OWN named rate limiter (`AppServiceProvider`); never use Laravel's string form `throttle:10,1`, which shares one counter per client across routes.
- **Categories**: the six activity categories are a fixed set (`Category::REQUIRED_NAMES`: Executive Function, Fine Motor Skills, Functioning Skills, Handwriting, Sensory, Visual). Admins cannot add, rename or delete them (only descriptions are editable); `category_id` is required and must be one of them when saving an activity. Migration `ensure_required_categories` adds a missing one idempotently. `php artisan activities:remove-test "<exact title>"... [--dry-run]` removes test activities by exact title with their progress and files. Outside `local`/`testing`, `AppServiceProvider` forces `app.debug` off.
- **Developer Team card**: one settings row (id 1, `developer_team`); `DeveloperTeam::current()` returns built-in sample details with `is_sample: true` until an admin saves it, and tolerates the table not existing yet.
- Tests are in `backend/tests/Feature` (RefreshDatabase). Users created without a role have `role` null in memory until `->fresh()`.
